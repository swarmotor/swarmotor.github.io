Deployment playbook

RECAP 实际部署具体分析

这份文档只谈落地：训练出来的 RECAP/CFG π0.5 策略如何从 checkpoint 变成 Isaac Sim 或真实机器人上的闭环控制系统。重点放在环境矩阵、模型产物、policy server、客户端 observation、动作 chunk、校准、延迟、安全、监控和回滚。

部署结论

能接上不等于能控制。 RECAP 部署的真正难点不是启动 server，而是让训练时的数据坐标系、推理时的 observation key、图像预处理、关节顺序、夹爪定义、action horizon、控制频率、初始位姿和安全边界全部一致。

Deployment target

1. 部署目标：把离线训练策略变成实时控制服务

RECAP 训练阶段输出的是一个经过 advantage-conditioned / CFG 训练的 OpenPI π0.5 policy checkpoint。部署阶段要做的事情，是把它包装成一个稳定服务，让仿真或真机每隔若干控制周期发送 observation，收到 action chunk，并安全执行。

部署验收标准：不是“代码能跑”，而是同一个任务 prompt、同一个初始位姿、同一个 observation schema 下，策略能稳定地产生形状正确、数值范围正确、时序连续、不会越界的动作，并且成功率高于 baseline SFT 或未 RECAP 的 π0.5。
层级部署对象必须一致的东西常见误判
模型层RECAP/CFG π0.5 checkpointconfig_name、checkpoint、norm stats、guidance scale只换 checkpoint，不确认 config 和数据 transform。
服务层OpenPI/RLinf policy serverPython 3.11、GPU、端口、序列化格式、batch/timeoutserver 能启动就以为部署完成。
客户端层Isaac Sim 或机器人控制程序observation key、图像尺寸、state 顺序、prompt字段名用官方泛化示例，但模型实际需要 DROID/LIBERO 专用 key。
控制层action chunk 执行器动作维度、单位、关节顺序、夹爪定义、控制频率机械臂“抽搐”被误认为模型差，而不是动作解释错。
安全层限幅、急停、回滚、监控workspace 边界、速度限制、异常动作拦截直接把模型输出喂给真机。
Runtime topology

2. 推荐部署拓扑：训练机/推理机跑 server，仿真或机器人跑 client

1

Camera/State

采集 RGB、wrist RGB、joint、gripper、task prompt。

2

Preprocess

RGBA→RGB，resize pad 到 224，state 按训练顺序组装。

3

Websocket

发送 observation 到 policy server，等待 action chunk。

4

Action Adapter

把模型动作转为 Isaac/机器人控制命令。

5

Safety Gate

限幅、碰撞、速度、夹爪、急停、日志。

GPU machine / workstation
------------------------------------------------------+
| openpi or RLinf env, Python >= 3.11, CUDA, checkpoint |
| uv run scripts/serve_policy.py ...                   |
+--------------------------^---------------------------+
                           | websocket, observation/actions
Isaac Sim / robot client   v
+------------------------------------------------------+
| openpi-client, camera/state adapter, action executor  |
| control loop, safety limit, logging, emergency stop   |
+------------------------------------------------------+

这种拆法的好处是：GPU 推理环境和 Isaac/机器人环境互不污染。特别是本地笔记指出 Isaac Sim 4.5 使用 Python 3.10，而 OpenPI/RLinf 通常要求 Python 3.11，部署时容易因为 Python 版本不一致卡住。Isaac Sim 5.0 或独立 robot client 更适合安装 openpi-client。

Artifacts

3. 部署前必须冻结的产物：不要只记一个 checkpoint 路径

RECAP 的部署产物至少包括四类：base policy 配置、CFG 训练 checkpoint、advantage 标签版本、推理参数。缺任何一个，复现就会变成“看起来加载了同一个模型，实际行为完全不同”。

产物例子部署时用途必须记录
Policy checkpointlogs/cfg_sft/.../checkpoints/global_step_N被 server 加载用于推理。绝对路径、step、训练命令、git commit。
OpenPI configpi05_droid、pi05_libero决定 observation transform、action dim、norm stats。config name 与训练时完全一致。
Advantage tagfail300_N10_ckpt18000_q30说明策略学的是哪一版优势标签。returns_tag、positive_quantile、N、value checkpoint。
Guidance 参数cfgrl_guidance_scale=1.0推理时控制高优势偏置强度。上线 scale、扫描范围、默认回退值。
Normalization stats训练数据统计server 端归一化 state/action。数据集版本、统计生成命令。
版本原则：一次部署只能对应一个不可变 manifest。manifest 里写清楚 checkpoint、config、数据集、returns_tag、advantage_tag、value checkpoint、guidance scale、action horizon、客户端 commit。没有 manifest，不上真机。
Environment matrix

4. 环境矩阵：先把 Python、CUDA、Isaac、OpenPI 分开

Server 环境

OpenPI/RLinf 推理侧

  • Ubuntu 22.04 更稳。
  • Python >= 3.11。
  • GPU 显存：推理通常至少 8GB，更复杂模型更高。
  • 用 uv 管理 OpenPI 仓库依赖。
  • checkpoint 可从本地路径或 gs:// 下载。
Client 环境

Isaac Sim / Robot 侧

  • 只需要轻量 openpi-client。
  • Isaac Sim 4.5 Python 3.10 可能不匹配。
  • Isaac Sim 5.0 更适合 Python 3.11 生态。
  • 不要在 Isaac 环境里装完整训练栈。
  • 客户端重点是采集、预处理和执行动作。
# OpenPI server side, from openpi/
GIT_LFS_SKIP_SMUDGE=1 uv sync
GIT_LFS_SKIP_SMUDGE=1 uv pip install -e .

# Client side, install lightweight websocket client
cd $OPENPI_ROOT/packages/openpi-client
pip install -e .
Policy server

5. Policy Server：先用假 observation 跑通，再接 Isaac

部署顺序一定是：本地单进程推理 smoke test → policy server 启动 → websocket client 假数据调用 → Isaac/机器人真实数据调用。不要一开始就把 Isaac 接进来，否则你无法区分是模型加载错、server 错、网络错、还是 observation 错。

# 示例：OpenPI pi0.5 DROID checkpoint server
cd /home/zj/PycharmProjects/pi0.5/openpi
uv run scripts/serve_policy.py policy:checkpoint \
  --policy.config=pi05_droid \
  --policy.dir=gs://openpi-assets/checkpoints/pi05_droid

如果是 RECAP 训练后的 checkpoint，把 --policy.dir 换成 Step 4 CFG 训练输出目录，并确保 --policy.config 与训练时的 OpenPI config 对齐。若 RLinf 的 CFG policy 使用不同启动脚本，需要以其 cfg_rl_openpi.yaml 中的 actor.model.model_path 和 actor.model.openpi.config_name 为准。

最常见错误：server 用 pi05_droid，客户端却按通用示例发送 observation/image 和 observation/wrist_image。DROID 实际常见 key 是 observation/exterior_image_1_left、observation/wrist_image_left、observation/joint_position、observation/gripper_position 和 prompt。 
# 最小 smoke test 的 observation 形状，来自本地 hello_pi05.py 经验
example = {
    "observation/exterior_image_1_left": np.zeros((224, 224, 3), dtype=np.uint8),
    "observation/wrist_image_left": np.zeros((224, 224, 3), dtype=np.uint8),
    "observation/joint_position": np.zeros(7, dtype=np.float32),
    "prompt": "pick up the fork",
}
action_chunk = policy.infer(example)["actions"]
print(action_chunk.shape)
Client adapter

6. Isaac/机器人客户端：observation adapter 是部署成败的核心

客户端每一轮控制循环要构造的不是“看起来差不多的 observation”，而是训练 transform 精确期望的 schema。字段名、dtype、shape、通道顺序、归一化职责必须明确。

字段推荐形状/类型来源必须检查
observation/exterior_image_1_left(224,224,3) uint8 RGB外部相机不是 RGBA；不是 BGR；resize_with_pad 后不拉伸。
observation/wrist_image_left(224,224,3) uint8 RGB腕部相机相机朝向与训练集一致。
observation/joint_position(7,) float32机械臂关节关节顺序、弧度/角度、零位、正方向。
observation/gripper_position(1,) float32夹爪开合0/1 哪个是开，是否与训练一致。
prompt字符串任务指令与训练 prompt 风格一致，不要临时换说法。
 
from openpi_client import image_tools
from openpi_client import websocket_client_policy

client = websocket_client_policy.WebsocketClientPolicy(host="localhost", port=8000)

def build_observation(exterior_rgba, wrist_rgba, joint_position, gripper, prompt):
    exterior_rgb = exterior_rgba[:, :, :3]
    wrist_rgb = wrist_rgba[:, :, :3]
    return {
        "observation/exterior_image_1_left": image_tools.convert_to_uint8(
            image_tools.resize_with_pad(exterior_rgb, 224, 224)
        ),
        "observation/wrist_image_left": image_tools.convert_to_uint8(
            image_tools.resize_with_pad(wrist_rgb, 224, 224)
        ),
        "observation/joint_position": joint_position.astype("float32"),
        "observation/gripper_position": np.array([gripper], dtype="float32"),
        "prompt": prompt,
    }
不要盲信夹爪转换：本地笔记里的左右夹爪位姿到 0-1 开合度转换只是初步方案。部署前要做物理标定：完全闭合、半开、完全打开三点采样，确认模型输出的 gripper 方向和仿真/真机控制方向一致。
Control loop

7. 控制闭环：action chunk 不是每一步都重新规划

OpenPI policy 往往返回一个 action chunk，形状类似 (action_horizon, action_dim)。部署时通常每隔 N 步推理一次，然后开环执行 chunk 中的若干步。关键是推理频率、执行频率、chunk 重叠策略要固定，否则策略训练时的时序假设会被破坏。

for episode in range(num_episodes):
    reset_to_known_initial_pose()
    action_chunk = None
    chunk_index = 0

    for t in range(max_steps):
        if action_chunk is None or chunk_index >= replan_interval:
            obs = build_observation(...)
            result = client.infer(obs)
            action_chunk = result["actions"]
            chunk_index = 0

        raw_action = action_chunk[chunk_index]
        safe_action = safety_filter(raw_action)
        execute_action(safe_action)
        chunk_index += 1
控制项具体要定错了的表现
Action dim每维代表 joint delta、absolute joint、EEF delta 还是 gripper。机械臂大幅抽搐或完全不动。
单位弧度/角度、米/厘米、归一化量/真实量。动作幅度放大或缩小 10-100 倍。
控制频率policy inference Hz 和低层 controller Hz。动作延迟、震荡、过冲。
重规划间隔执行 chunk 的几步后重新 infer。太短会抖，太长会错过反馈。
夹爪策略连续控制、阈值开关还是延迟执行。夹爪提前闭合、永远不闭合或反向。
Calibration

8. 校准清单：机械臂“抽搐”通常不是模型问题

相机外参
训练时外部相机在左前还是右前？Isaac 相机是否镜像？图像是否上下翻转？
图像颜色
Isaac 输出 RGBA，必须去 alpha；如果是 OpenCV 路径，还要确认不是 BGR。
关节顺序
训练数据 joint_0...joint_6 与 Isaac articulation 顺序是否一致，不能只看维度都是 7。
关节单位
确认 state 是 rad 还是 degree；action 是 delta 还是 target。
夹爪方向
0 是闭合还是打开；左右 finger 是否对称；是否需要取平均。
初始位姿
初始 pose 与训练/评测环境差一点，VLA 可能完全分布外。
prompt 风格
不要把训练中 “pick up the fork” 临时改成中文或复杂长句。
动作限幅
部署第一天必须限速度、限位置、限夹爪力，先保守后放开。
RECAP-specific deployment

9. RECAP 特有部署项：CFG scale 和正样本偏置要单独上线

普通 π0.5 SFT 部署只需要确认 checkpoint 和 transform。RECAP 多了一个变量：推理时是否启用 advantage-conditioned/CFG，以及 guidance scale 多大。这个变量会直接改变动作分布，不能和普通模型一样“一次上线”。

部署模式含义适用阶段风险
Baseline SFT未 RECAP 的原始 π0.5。对照组。性能可能低，但行为更熟悉。
RECAP, scale=1使用条件策略，但不强烈放大。首个 RECAP 部署点。提升可能温和。
RECAP, scale>1放大高优势方向。仿真扫描后再考虑。动作更激进，可能越界或抖动。
RECAP, scale=0 或 uncond近似普通行为分布。回滚/诊断。不体现 RECAP 增益。
上线规则：不要直接把 cfgrl_guidance_scale 调高上真机。先在仿真或离线回放中扫 0, 0.5, 1.0, 1.5, 2.0，观察动作幅度、夹爪时机、碰撞率、成功率，再选择最小可用 scale。
Failure diagnosis

10. 故障定位：按现象反推是哪一层错

现象优先怀疑具体检查修复方向
server 启动失败环境/权重/configPython 版本、CUDA、checkpoint 路径、config name。先用 hello_pi05 式本地 fake obs 推理。
client 报缺字段observation key 不匹配查看 policy example/schema，确认 DROID/LIBERO key。改 adapter，不改模型。
动作 shape 不对config 或 checkpoint 错action_dim、action_horizon、robot_type。核对训练 manifest。
机械臂抽搐动作解释/单位/关节顺序逐维打印 action，单维注入测试。建立 action adapter 和限幅。
能动但任务失败初始位姿/相机/prompt 分布外对比训练数据首帧和部署首帧。重置场景、采集微调数据。
RECAP 比 SFT 更差advantage 标签或 scalescale=0/1/更高对照，查看高优势动作是否合理。降低 scale，重标 q20/q30，重训。
延迟导致错过物体网络/推理频率/chunk 策略记录 capture→infer→execute 延迟。客户端 resize，减少传输，调 replan interval。
Rollout plan

11. 从仿真到真机的上线流程：每一步都有停止条件

Phase 0

离线验证

fake observation 推理成功，action shape 正确，server/client websocket 正常，manifest 完整。

Phase 1

仿真空动作

Isaac 中只打印动作不执行，确认 latency、shape、数值范围、字段。

Phase 2

仿真限幅执行

低速、短 episode、固定初始位姿，先看是否安全，再看任务成功。

Phase 3

仿真批量评估

baseline vs RECAP scale 扫描，统计成功率、碰撞、超时、动作幅度。

Phase 4

真机影子模式

真机采集 observation，模型只输出建议动作，不执行，比较人工/现有控制。

Phase 5

真机受控上线

低速、急停、人值守、小范围 workspace，逐步放开。

最终交付物：部署 manifest、server 启动脚本、client adapter、action adapter、安全过滤器、评估日志、失败视频、scale 扫描表、回滚命令。没有这些，不能称为“实际部署完成”。
